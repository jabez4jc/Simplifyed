# Phase 0 implementation — C1–C5

Date: 2026-10-02. Baseline commit: `bca9c4d` on `main`. Five commits, one per item, `9f69373`..`716ad37`.

## Per-item summary

### C1 · Background services start only when a browser logs in
- **Changed:** `server.js` now calls `startBackgroundServices()` unconditionally inside the `server.listen` callback, right after the HTTP listener binds, instead of lazily on the first authenticated request. Removed `app.locals.startServices` and both lazy-start call sites in `src/middleware/auth.js`. Added `process.on('unhandledRejection', ...)` and `process.on('uncaughtException', ...)` (the latter logs then `process.exit(1)`). Wrapped the `settings:changed` listener body in try/catch.
- **Tests added:** none required an automated test per the report (manual/log-based accept criteria). Verified by booting the server against a throwaway DB copy with zero HTTP requests and confirming "Market data feed service started", "Auto exit service started" and "Polling service started" all log on boot.
- **Skipped:** nothing.

### C2 · Concurrency slot leak deadlocks all non-skip broker calls
- **Changed:** `src/integrations/openalgo/client.js`. Split `_waitForConcurrency` into `_waitForConcurrencySlot` (wait + increment) and `_waitForRateBucket` (the token-bucket wait, which can throw a 429). Restructured `_executeWithConcurrency` so the slot is acquired *before* a `try`, and both the bucket wait and the request itself run *inside* that `try`, with the `finally` releasing the slot — so a bucket throw can no longer leak a slot. Made `currentTasks` a `Map<instKey, count>` instead of one global counter, so one hung broker can no longer starve every other instance. Updated `getRateBudgets()`'s `currentConcurrent`/`concurrentSlots` to read per-instance.
- **Tests added:** `Test/unit/openalgo-concurrency-slot.test.js` — (1) the bucket throws 11 times in a row with `maxConcurrentTasks=1`, then a 12th call must resolve and the slot must be back at 0 (would hang forever under the old bug); (2) the limit is per-instance, not global (instance A holding its only slot does not block instance B).
- **Skipped:** nothing.

### C3 · A retry or close-retry cancels EVERY open order on the account
- **Changed:** `src/services/order-retry.service.js` — the one call site using `_cancelAllForRetry` now calls the existing symbol-scoped `_cancelOpenOrdersForSymbol` instead; deleted `_cancelAllForRetry` and its now-unused helper `_cancelAll` (and the now-dead `orderService` import). `src/services/quick-order.service.js` — rewrote `_cancelAllOrdersForRetry` in place to fetch the live orderbook and cancel only orders matching the close's own symbol/exchange/product (via `openalgoClient.cancelOrder` per id), instead of calling `orderService.cancelAllOrders` (OpenAlgo's account-wide `cancelallorder`). `src/services/order.service.js` — `cancelAllOrders` no longer blanket-marks every local pending/open row cancelled after the broker call; it now defers to the existing `syncOrderStatus` orderbook reconciliation (same pattern already used after order placement).
- **Tests added:** `Test/unit/retry-symbol-scoped-cancel.test.js` — two tests, one per call site, each with a stubbed `openalgoClient.cancelAllOrders` that throws if called at all, proving retrying/closing symbol A only ever cancels A's own open order ids.
- **Skipped / note:** `_cancelAllOrdersForRetry`'s name was **not** deleted — its body was rewritten to be symbol-scoped, kept under the same name because `Test/integration/close-retry.test.js` already stubs it by name to isolate retry-decision logic, and the fix text explicitly allows "use the one in the same service" without mandating cross-service reuse this phase (P3-6 is where the two symbol-scoped-cancel copies get merged into one util). So the final sanity grep for `_cancelAllOrdersForRetry` in §9.3 will still find one hit until P3-6; the account-wide-cancel bug itself (what C3 is actually about) is fully fixed and tested.

### C4 · TradingView broadcast re-sends orders and bypasses every safety layer
- **Changed:** `src/services/tradingview-broadcast.service.js` — broadcast dispatch now goes through `order.service.placeOrder` (same path and `watchlist_orders` recording as every other order source) instead of POSTing `placesmartorder` straight to OpenAlgo over its own `fetch`/retry loop. Deleted: the local `TokenBucket` class, `_postWithRetries`, `_postJson`, `_retryDelay`, `_ensureLimitPricing`, `_marketOrRefuse`, `_resolveBufferPct`, `_roundToTick`, `_countDecimals`, `_resolveTickSize`, `_scheduleRetryForTarget` (retry is now automatic inside `order.service`/`order-placement.service` for LIMIT orders). `assertAuthorized` no longer falls back to `process.env.WEBHOOK_TOKEN`. Deleted the dead config keys `config.webhooks.tradingviewBroadcast.{timeoutMs,retries,retryDelayMs,defaultRps,bufferPctDefault,bufferPctByStrategy}` and `parseStrategyBufferConfig`/`getEnvFloat` in `src/core/config.js`. Deleted the `TRADINGVIEW_BUFFER_*` keys from `.env.example` and the stale `TRADINGVIEW_BROADCAST_*` entries from `update.sh`'s optional-env-key allowlist. `watchlistService.getBroadcastTargets` no longer returns `url`/`endpoint`/`apikey`/`rateLimit`/`key`/`broker`/`is_analyzer_mode`/`multiplier` — nothing outside this service read them.
- **[OWNER] O3 applied:** dropped `watchlists.limit_buffer_pct` via new migration `071_drop_watchlist_limit_buffer_pct.js` (tested against a throwaway copy of the real DB — applies cleanly, column confirmed gone), and removed its UI field from `dashboard-watchlists-modals.js` and `dashboard-instances.js`. Bumped `?v=` for both files plus `dashboard.html`.
- **Side fix:** `order.service.placeOrder`'s signal counting always tagged orders `manual_buy_signals`/`manual_sell_signals` regardless of source; now tags `webhook_buy_signals`/`webhook_sell_signals` when `source === 'webhook'`, so broadcast orders routed through this shared path don't get mis-labelled (and aren't double-counted, since broadcast's own separate counting block was deleted).
- **Tests added:** `Test/unit/tradingview-broadcast-safe-dispatch.test.js` — a stubbed `orderService.placeOrder` shows a broadcast alert calls it exactly once per target with no internal retry, both on success and on a rejection (which is reported, not swallowed or retried).
- **Verified live:** re-ran at G1 against the real crypto instance — "an authorised alert actually reaches the instance behind the watchlist" passed, with logs showing the full `[OrderPlacement] Dispatching placesmartorder` → `Order placed successfully` path (confirms the rewrite works end-to-end, not just in the stub).
- **Skipped:** nothing.

### C5 · Session P&L counts open positions at full notional
- **Changed:** added `computeSessionPnl(positions, tradebook, brokerageValue)` to `src/utils/trade-pnl.js` — the broker's own per-position MTM (qty=0 row is realized, non-zero is unrealized) minus today's charges, extracted from `dashboard.service.js`'s existing (correct) definition. `src/services/instance-pnl.service.js`'s `updatePnLData` now fetches the position snapshot and calls this function for `totalPnl` (which feeds the session cutoff check) instead of `calculateTradebookPnL(tradebook).net_pnl` (a buy/sell-value reconstruction that priced any untouched open position at full notional). It also now persists the real `realized_pnl`/`unrealized_pnl` instead of hardcoded `0` (that DB column is read as a fallback for inactive instances in `dashboard-instances.js`, so dropping it would have made that column permanently stale — writing the real value was strictly better than deleting). `dashboard.service.js`'s `_fetchInstanceFunds` now calls the same shared function instead of its own inlined copy of the same logic. Both the brokerage-default `20` hardcodes (one in each file) now read from `settingDefault('brokerage.default')`.
- **Tests added:** `Test/unit/session-pnl.test.js` — four tests: an open BUY with no SELL prices at MTM (not full notional loss); an open SHORT prices at MTM (not a notional profit); a flat (qty=0) position is realized with charges netted in; and the empty-input zero case.
- **Skipped:** nothing. (The "dashboard and session check return the same number for the same inputs" accept criterion is satisfied structurally — both now call the one shared function — rather than by a separate cross-service integration test.)
